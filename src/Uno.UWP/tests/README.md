# WebAssembly storage regression tests

These tests use the existing TypeScript compiler, Node's built-in test runner, and an existing Playwright installation. They do not add package dependencies.

From the repository root, compile the production storage implementation with the Emscripten declarations and a declaration for its initialization dependency:

```powershell
$tsc = Join-Path $env:NUGET_PACKAGES "microsoft.typescript.msbuild\4.3.5\tools\tsc\tsc.js"
New-Item .\artifacts\storage-tests -ItemType Directory -Force | Out-Null
node $tsc .\src\Uno.UWP\ts\Windows\Storage\StorageFolder.ts `
  .\src\Uno.UI\ts\types\emscripten\index.d.ts `
  .\src\Uno.UWP\tests\storage-folder-environment.d.ts `
  --target ES2017 --lib ES2018,DOM --noImplicitAny `
  --outFile .\artifacts\storage-tests\StorageFolder.js
$env:STORAGE_FOLDER_SCRIPT = ".\artifacts\storage-tests\StorageFolder.js"
node --test .\src\Uno.UWP\tests\storage-folder.cjs
node $tsc --project .\src\Uno.UWP\tsconfig.json --noEmit
```

`storage-folder.cjs` uses controlled filesystem callbacks and timers. It covers ordering, individual acknowledgements, error propagation (including falsy thrown values), timeout/late-callback safety, initial restoration, disabled persistence, owned versus external mounts, no-op rejection, additional mounts, and best-effort lifecycle hooks. These are mocked-backend tests, not IndexedDB durability tests.

For real IndexedDB validation, run a built WebAssembly application with IDBFS enabled, set `PLAYWRIGHT_MODULE` to an existing `playwright-core` installation if it is not on Node's module path, and run:

```powershell
$env:PERSISTENCE_BROWSER_PROFILE = ".\artifacts\storage-tests\browser-profile"
node .\src\Uno.UWP\tests\storage-folder-browser.cjs "http://localhost:PORT/"
```

The browser test loads the compiled storage JavaScript into the running app, uses real Emscripten IDBFS mounts with unique names, and immediately reloads after acknowledged checkpoints. It also checks concurrent checkpoints and that populating an additional mount does not overwrite unpersisted files. It uses an isolated Edge profile, not the user's browser profile.

This injected-JavaScript test **does not rebuild or validate managed initialization**. Use the compiled fixture below for that boundary. Do not combine the changed JavaScript with an older managed assembly in a deployed app: managed initialization now awaits the JavaScript task rather than a separate exported callback.

## Compiled managed/WebAssembly integration

`tests\Uno.UWP.Persistence.Wasm` uses the installed .NET WebAssembly SDK and directly references source-built Uno assemblies. It does not overlay or modify any NuGet package. Its entry page loads the JavaScript generated by the same `Uno.Wasm.csproj` build.

Build serially from the repository root. If a project reports missing assets, restore that project before rebuilding. For isolated dependency storage, pass `RestorePackagesPath` pointing to an owned directory and `RestoreFallbackFolders` pointing to the existing package cache to both restore and build.

```powershell
dotnet build .\src\Uno.UWP\Uno.Wasm.csproj -c Release -f net10.0 `
  -p:UnoTargetFrameworkOverride=net10.0 -m:1 --no-restore
dotnet build .\src\Uno.UWP\Uno.Wasm.csproj -c Release -f net10.0 `
  -p:UnoTargetFrameworkOverride=net10.0 -p:BuildProjectReferences=false `
  -t:Rebuild -m:1 --no-restore
New-Item .\artifacts\persistence-fixture -ItemType Directory -Force | Out-Null
node $tsc .\src\Uno.UI\ts\Interop\Runtime.ts `
  .\src\Uno.UI\ts\Interop\AsyncInteropHelper.ts `
  --target ES2017 --lib ES2018,DOM `
  --outFile .\artifacts\persistence-fixture\Uno.Interop.js
dotnet build .\tests\Uno.UWP.Persistence.Wasm\Uno.UWP.Persistence.Wasm.csproj `
  -c Release -m:1 --no-restore
python -m http.server 5000 --bind 127.0.0.1 `
  --directory .\tests\Uno.UWP.Persistence.Wasm\bin\Release\net10.0\wwwroot
```

The targeted rebuild ensures that TS-only edits are reflected in the assembly's embedded resource, not just the generated `.js` file. Before packaging, verify that `Windows.WasmScripts.Uno.Wasm.js` embedded in `Uno.dll` has the same bytes as `bin\Uno.Wasm\Release\net10.0\javascript\Uno.Wasm.js`; an incremental build can otherwise retain an earlier embedded script. No shared build targets need to be changed.

In a second terminal, with the existing Playwright module available:

```powershell
$env:PERSISTENCE_BROWSER_PROFILE = ".\artifacts\persistence-fixture-profile"
node .\tests\Uno.UWP.Persistence.Wasm\run.cjs "http://127.0.0.1:5000/"
```

The seven scenarios execute real compiled C# `WebAssemblyRuntime.InvokeAsync` and the actual managed `JSImport` initialization path. They verify:

- `Promise<void>` completes the public bridge with `null`; projecting it to a string produces an explicit acknowledgement.
- Concurrent checkpoints reach real IndexedDB before navigation and restore after reload.
- Checkpoints reject when there are no Uno-owned mounts, including when only external mounts exist; later initialization remains possible.
- Initializing an unrelated cache mount does not open the global application-data gate.
- Concurrent application-data initialization waits for the final mount.
- Startup failure faults pending storage operations and subsequent checkpoints.
- Disabled persistence permits in-memory startup but rejects checkpoints.

This is a non-UI fixture: it loads the real exports and releases the normal export-ready gate without constructing a window/dispatcher. Reflection invokes the internal application-data initializer, so the fixture is intentionally untrimmed. The failure scenario injects a browser `IndexedDB.open` denial; the concurrency scenario delays the completion callback of the final real restoration. Those are controlled fault/timing tests, not claims of naturally occurring browser failures. The checkpoint/reload scenarios use real IDBFS and IndexedDB without backend substitution.

Application-level SQLite integration also needs an explicit startup barrier before creating a connection: await `StorageFolder.GetFolderFromPathAsync` for the database's actual application-data directory, under the shared asynchronous database-operation lock. For .NET MAUI, that directory can be `FileSystem.AppDataDirectory`. Do not substitute `GetItemsAsync` or `GetFilesAsync`: empty enumerations can return without awaiting the initialization gate. `OnLaunched` is not a barrier either, because browser application startup does not await persistence initialization before scheduling it.

Serialize writes and await a checkpoint after committing the transaction. This fixture does not make an unmodified SQLite save durable, and an acknowledged checkpoint does not replace the startup barrier on reload.
